# VJ Test Kitchen (iOS)

Native SwiftUI rebuild of VJ Test Kitchen — a recipe manager with AI-powered menu planning. Replaces the old React/Express/Railway stack entirely; there is no website. See global `~/.claude/CLAUDE.md` for the mandatory TDD workflow and commit conventions this repo follows — not repeated here.

Prior web app (reference only, not integrated, not deployed): `/Users/bvj13/source/vj-test-kitchen`. Its Postgres schema (`backend/db.js`) and feature set are the starting point for this rebuild's data model and scope, but no code is shared or ported directly.

## Architecture
- **Client**: Native SwiftUI, universal iPhone + iPad **+ native macOS** (Swift 6, MVVM). Deployment target: **iOS 26 / iPadOS 26 / macOS 26 minimum** (bumped from 18 for Liquid Glass — see DECISIONS.md, 2026-07-06; macOS pinned to 26 for the same Liquid Glass identity, no non-glass fallbacks). Built with Xcode 26+. The macOS app is a **second native target** (`VJTestKitchenMac`), not Catalyst / "Designed for iPad" — see the cross-platform Conventions bullet.
- **Design language**: Liquid Glass throughout (`.glassEffect()`, `GlassEffectContainer`, `.glassProminent` button style) — this is a deliberate visual identity choice, not just "whatever's default." Standard components (`TabView`, `NavigationStack`/`NavigationSplitView` toolbars, sheets) get it automatically from the iOS 26 SDK; custom cards/overlays/floating controls should opt in explicitly to stay visually consistent with system chrome.
- **Backend**: Supabase — Postgres (with Row Level Security), Supabase Auth, Supabase Storage for images/files, Supabase Edge Functions for server-side logic.
- **AI planner**: Google Gemini (`gemini-3.1-flash-lite`, carried over from the old app for its free-tier quota) called from a Supabase Edge Function. The Gemini API key lives only as a Supabase secret — never shipped in the client.
- **Networking**: `supabase-swift` SDK, async/await throughout (no completion-handler APIs).
- **Testing**: Swift Testing (`@Test`/`#expect`), not XCTest.
- **Bundle identifier**: `com.bvj303.vjtestkitchen`.

## Folder structure
```
project.yml                 # xcodegen spec — source of truth; VJTestKitchen.xcodeproj is generated, gitignored
Config/
  Secrets.xcconfig           # real values, gitignored
  Secrets.xcconfig.example    # tracked template
VJTestKitchen/
  App/                  # App entry point (VJTestKitchenApp.swift)
  Models/                # Codable structs matching Postgres tables (Recipe, RecipeRating, Ingredient, Tag, MealPlan, Profile)
  Services/              # AppConfig, SupabaseDecoding, SupabaseManager (client singleton), one Service struct per resource
  ViewModels/             # MVVM view models, one per screen/feature (empty until Stage 5)
  Views/                  # SwiftUI views, grouped by feature
  Resources/              # Info.plist (custom, NOT auto-generated — see below), assets
VJTestKitchenTests/       # Swift Testing unit tests
```

Regenerate the Xcode project any time `project.yml` changes: `xcodegen generate`.

**This is automated so a stale `.xcodeproj` can't silently break the build** (the class of bug where a pull that changed `project.yml` left the gitignored project pointing at a deleted file — e.g. the WeatherKit `CODE_SIGN_ENTITLEMENTS` reference). Two layers, both keyed off the fact that the gitignored `.xcodeproj` is only ever *older* than `project.yml` when regeneration is actually due:
- **Git hooks** (`.githooks/`, run `./.githooks/install.sh` once per clone to set `core.hooksPath`) regenerate on `post-merge`/`post-checkout`/`post-rewrite` — i.e. after a pull, branch switch, or rebase, before you ever build. Two drift signals (`xcodegen-sync.sh`): (1) `project.yml` content changed (mtime — the gitignored project ends up older than the spec), and (2) a source file was **added/renamed/removed** (which never touches `project.yml`, since sources are globbed — detected by diffing the tracked `*.swift` set against what the generated project references). Signal 2 is the important one: without it, pulling a branch that adds a new `.swift` file leaves the stale project missing it and the build fails with `cannot find <NewType> in scope`.
- **An Xcode pre-build guard** (`preBuildScripts` in `project.yml`, so it survives regeneration) *fails the build with a fix message* if `project.yml` is newer than the generated project. It deliberately does not regenerate mid-build (Xcode has already loaded the old project into memory — rewriting it underneath a running build is racy); it's the safety net for a hand-edited `project.yml` that the hooks can't catch.

## Configuration & secrets
- **Supabase project**: ref `aviyhrmjsqygoyzjprii`, region `us-east-2`, Postgres 17. Repo is linked via `supabase link` (uses `SUPABASE_ACCESS_TOKEN` from the developer's shell profile, never committed).
- **Project URL + anon/publishable key** (`sb_publishable_...`): safe to embed client-side by design — security is enforced by RLS policies, not by hiding this key. Real values live in `Config/Secrets.xcconfig` (gitignored; `Config/Secrets.xcconfig.example` is the tracked template) and a repo-root `.env` (gitignored, for shell/CLI use). xcconfig treats `//` as a comment start, so URLs are written as `https:/$()/host` to escape it.
- **The app target uses a custom `VJTestKitchen/Resources/Info.plist`, not `GENERATE_INFOPLIST_FILE`** — Xcode's auto-generated-Info.plist + `INFOPLIST_KEY_*` mechanism only synthesizes a fixed list of Apple-known keys (launch screen, orientations, etc.) and **silently drops arbitrary custom keys** like `SUPABASE_URL`. Custom keys must go in a real Info.plist file with `$(SUPABASE_URL)`-style variable substitution. `Info.plist` is excluded from the target's `sources` copy-resources step (it's consumed via `INFOPLIST_FILE`, not copied as a resource) — see `project.yml`.
- `AppConfig` (`Services/AppConfig.swift`) reads these via an injectable `Bundle` parameter (defaulting to `.main`). This isn't just DI-for-its-own-sake: unhosted Swift Testing unit tests do **not** run inside the app process, so `Bundle.main` inside a test resolves to the test bundle, not the app — tests must build and inject a synthetic `Bundle` (real temp-directory-backed, with its own `Info.plist`) to exercise `AppConfig`'s parsing logic. See `AppConfigTests.swift`.
- **`service_role` key and the Gemini API key are true secrets** — full DB access bypassing RLS, and paid API access, respectively. They live only as Supabase Edge Function secrets (`supabase secrets set`), never in the client, never in `.env`, never committed.
- Prefer Supabase's newer `sb_publishable_...` / `sb_secret_...` key naming over the legacy anon/service_role JWTs when either is exposed in the dashboard — same roles, newer scheme.
- **An `AppIcon`/`AccentColor` asset alone does nothing without an explicit build setting** — since this project sets `GENERATE_INFOPLIST_FILE: NO`, Xcode's usual "just name it AppIcon/AccentColor" convenience doesn't kick in automatically. `project.yml` must set `ASSETCATALOG_COMPILER_APPICON_NAME: AppIcon` and `ASSETCATALOG_COMPILER_GLOBAL_ACCENT_COLOR_NAME: AccentColor` explicitly, same category of gotcha as the custom Info.plist above. Easy to miss because the asset catalog compiles fine either way — only the missing wiring is silent.

## Conventions
- **Cross-platform (iOS + macOS)**: one shared `VJTestKitchen/` source tree feeds **two `application` targets** — `VJTestKitchen` (iOS, `Resources/Info.plist`) and `VJTestKitchenMac` (macOS, `Resources/Info-macOS.plist`) — both globbing the same sources in `project.yml`, so any new file lands in both automatically. Chosen over xcodegen's `platform: [iOS, macOS]` templating because the Info.plists genuinely diverge (macOS drops `LSRequiresIPhoneOS`/orientations) and it matches the repo's "explicit over Xcode-magic" ethos. Two gotchas baked into the mac target's settings: it pins `PRODUCT_MODULE_NAME: VJTestKitchen` (so the shared tests' `@testable import VJTestKitchen` resolves) while leaving `PRODUCT_NAME` = the target name (so xcodegen's auto-derived `TEST_HOST` path resolves — a `PRODUCT_NAME` override there breaks the hosted test bundle); the display name comes from a literal `CFBundleName` in the mac plist instead. Each platform has its own scheme (`VJTestKitchen`, `VJTestKitchenMac`) and its own unit-test target sharing the same `VJTestKitchenTests/` sources. **All platform-specific code is confined to `VJTestKitchen/Platform/`** — do not scatter `#if os(...)` across feature code; add to these shims instead: `PlatformColor`/`PlatformImage` typealiases (+ `Color.dynamic`, `Color.platformBackground`/`platformGroupedBackground`, `Image(platformImage:)`), `KeepAwake` (idle-timer vs `ProcessInfo.beginActivity`), and `View+CrossPlatform.swift`'s wrappers for the iOS-only SwiftUI modifiers (`inlineNavigationTitle`, `platformKeyboardType`, `platformAutocapitalization`, `platformMediumLargeDetents`, `platformFullScreenCover` → sheet on mac, `platformInsetGroupedListStyle`, and `ToolbarItemPlacement.platform{PrimaryAction,Cancellation,Leading}` mapping the iOS-only `.topBar*` placements). `AvatarImageProcessor` was rewritten to pure ImageIO (no UIKit/AppKit) so it's one code path on both. Swipe actions are `#if os(iOS)`-guarded with the same action mirrored into an always-present `.contextMenu` (so macOS right-click and iPad pointer reach it). Mac-native App-layer polish (menu-bar `.commands` for ⌘N/⌘F/⌘R/⌘1–5, the `Settings` ⌘, scene, `.windowResizability`/`.defaultSize`) lives in `App/VJTestKitchenApp.swift`, driven by an `AppCommands` (`App/AppCommands.swift`) `@Observable` command bus injected into the environment. **⌘N is context-aware**: `AppCommands` mirrors the visible tab (`currentTab`, set by `MainTabView` from its `selection`) so `requestNew()` routes to that tab's add action — a new grocery item on Groceries, a new recipe everywhere else — and the File ▸ New menu *title* (`newItemTitle`) tracks it live ("New Grocery Item" vs "New Recipe"), the way native Mac apps do. Consumers: `MainTabView` consumes `pendingTab` (and publishes `currentTab`); `RecipeListView` the new-recipe/search counters; `GroceryListView` the new-grocery-item counter; and `RecipeListView`/`GroceryListView`/`HomeView`/`MealCalendarView` each observe `refreshRequests` (⌘R reloads whichever tab is visible). Add a new context-aware create by extending `AppCommands.requestNew()`/`newItemTitle` + an `onChange(of:)` counter observer in the target view — don't add a second always-on ⌘N. `.commands` is left **unfenced** so iPad hardware keyboards get the shortcuts too. Routing is unit-tested (`AppCommandsTests`). The mac target runs under **App Sandbox** (`Resources/VJTestKitchen-macOS.entitlements`, wired via `CODE_SIGN_ENTITLEMENTS`): `app-sandbox` + `network.client` (Supabase/Open-Meteo/images) + `personal-information.location` (weather) + `personal-information.calendars` (Reminders export — Reminders shares the calendars entitlement domain, there is no separate `reminders` key). The sandbox also gives the app a **per-app keychain**, which is what stops the repeated "allow keychain access" prompts an unsandboxed build gets for its Supabase session token. Signing is still **local dev only** (Mac App Store / Developer ID is a later step); for local runs, sign with the installed Apple Development identity rather than ad-hoc `-` — an ad-hoc signature changes every build, so macOS re-prompts for keychain access each launch, whereas a stable Development cert's grant persists.
- MVVM: Views own no business logic; ViewModels are `@Observable` (or `ObservableObject` if needed) and talk to Services; Services own all Supabase calls.
- All Supabase/network calls are `async throws`, called from ViewModels via `Task { }`.
- Session persistence is Keychain-backed (via supabase-swift's built-in secure storage), not UserDefaults.
- Postgrest filter values (`.eq`, etc.) must be passed as `String` — `Int64` does not conform to `PostgrestFilterValue` in supabase-swift 2.x. See `RecipeService.swift`.
- `SupabaseDecoding.decoder`/`.encoder` (shared `JSONDecoder`/`JSONEncoder`) handle snake_case<->camelCase conversion and Postgres `timestamptz` parsing (with or without fractional seconds) for all models — always decode/encode Postgrest payloads through these, not a bare `JSONDecoder()`. Postgres `date` columns (e.g. `meal_plans.date`) are the exception: kept as a plain `"yyyy-MM-dd"` `String` on the model since the shared decoder's date strategy is timestamp-oriented.
- `RecipeService` is the reference pattern for the Service layer (one struct per resource, thin async/await wrappers, Codable in/out) — replicate its shape for ingredients/tags/recipe_ratings/meal_plans as Stage 5 needs them.
- Auth follows the same protocol-abstraction pattern: `AuthServicing` (real impl `AuthService`, wraps `client.auth`) is what `AuthViewModel` depends on, never `SupabaseClient` directly — keeps view models unit-testable without a network/session, and keeps SDK-specific types (`Session`, `User`) out of the ViewModel layer. `AuthViewModel.state` (`.loading`/`.signedOut`/`.signedIn(userId:)`) drives `RootView`'s top-level gating between `AuthView` and the signed-in app (`MainTabView`).
- Sign-up is a **single page** (`CreateAccountView`, pushed from `AuthView`'s "Create Account" link, bound to the shared `AuthViewModel`): first/last name, username (with live availability), email, and password on one form, with `AuthViewModel.signUp()` gated on `canSubmitSignUp` (profile fields valid + non-empty email + password ≥ minimum). This replaced the earlier two-step `CreateProfileView` → `CreateAccountView` flow — the separate profile screen was consolidated in, and `canProceedToAccountStep` is kept only as the profile-fields building block of `canSubmitSignUp`. Username availability is checked live via `ProfileService.isUsernameAvailable` (a `security definer` Postgres RPC granted narrowly to `anon`, since the user has no session yet at this point — see `profiles_first_last_username` migration) through the same `Debouncer` pattern as recipe/calendar search. `AuthServicing.signUp` passes firstName/lastName/username to Supabase Auth's `data:` param (user metadata); `handle_new_user()` copies them into `profiles` and derives `display_name` as "First Last". The DB's case-insensitive unique index on `username` is a race-condition safety net, not the primary UX gate — rely on the pre-check RPC for a friendly "taken" message, since a trigger-level failure surfaces as a generic GoTrue error.
- Account/profile access: a toolbar `AccountButton` (`person.crop.circle`, present on every tab via `PlaceholderTabView` and `RecipesTab`) presents `ProfileView` as a sheet. Matches Apple's own apps (App Store, Music, Photos) — a dedicated page for account actions, not an inline menu, once there's more than one trivial action. `ProfileView` hosts an "Edit Profile" row (pushes `EditProfileView`/`ProfileViewModel` — loads via `ProfileService.fetchMine()`, saves via `updateMine(firstName:lastName:username:)`, which resolves the signed-in user internally like `RecipeRatingService` and re-derives `display_name` so it can't go stale), Sign Out, and Delete Account (destructive-confirmation-gated — App Store Guideline 5.1.1(v) requires in-app deletion for any app with account creation; deletes via the `delete-account` Edge Function, service_role-backed). On iPad's `NavigationSplitView`, this button lives on the detail column's toolbar, not the sidebar's — the sidebar's trailing slot is already taken by the system sidebar-collapse toggle.
- `ProfileViewModel`'s username-availability check reuses sign-up's debounced-RPC-check flow (see the Sign-up bullet above) but adds an `.unchanged` state: re-entering the profile's own current username is trivially fine to save without a network round-trip or a confusing "available" message. The format regex itself lives in a shared `UsernameFormat` enum (`Models/UsernameFormat.swift`) so sign-up and editing validation can't drift apart — extend that, not a per-view-model copy, if the format ever changes.
- Profile pictures (avatars): the app's **first and only Supabase Storage feature** (recipe cover photos, `image_path`, are still Stage-6-reserved and unimplemented). `profiles.avatar_url` holds a public URL — same shape as `recipes.image_url`, and world-readable to others for free via the existing `profiles_select_all` policy, so "others can see it" needs no new profiles policy. Images live in a **public** `avatars` bucket at `<uid>/avatar.jpg`; the bucket + `storage.objects` RLS (public read; insert/update/delete gated on `(storage.foldername(name))[1] = auth.uid()::text`, i.e. you can only write your own `<uid>/…` folder) are created by the `profile_avatars` migration — **not** `config.toml`, so `db push` provisions them on remote too (a `config.toml` bucket block would also double-up and trigger an "already exists, overwrite?" prompt on `db reset`). `ProfileService.uploadAvatar(_:)` uploads (upsert, `contentType: image/jpeg`), writes a **cache-busted** (`?v=<epoch>`) public URL onto the profile row (the object path is stable across re-uploads, so without the bust AsyncImage/CDN would keep serving the old picture), and returns it. Client downsizes to a ≤512px JPEG via `AvatarImageProcessor` (`Services/`, UIKit, unit-tested) before upload — keeps uploads small and makes the bytes actually match the declared JPEG type (a full-res HEIC mislabeled as JPEG renders wrong). Editing lives in `EditProfileView` (a `PhotosPicker` that uploads **immediately on pick**, independent of the Save button for name/username — so the picture isn't lost if the user backs out); `ProfileView` shows the avatar in a header. Both share **one** `ProfileViewModel` (injected into `EditProfileView`) so an upload in Edit reflects in the Profile header live — needed because Edit is a `NavigationLink` push, not a sheet, so ProfileView's `.task` doesn't re-fire on return. `AvatarView` (`Views/Shared/`) is the reusable circular image (AsyncImage + initials/person fallback) — reuse it anywhere another user's avatar is shown. PhotosPicker needs no `NSPhotoLibraryUsageDescription` (out-of-process picker) and Storage/network need no new PrivacyInfo reason code. **Remote activation:** the migration must be applied to the linked remote project (`supabase db push`) before uploads work in the app, which targets remote.
- Supabase project has `mailer_autoconfirm = true` (Auth config) for solo testing — signups get an active session immediately, no email-confirmation click-through. **Must flip back to `false`** before inviting another real user or shipping (see DECISIONS.md, 2026-07-06).
- `RecipeRatingService` resolves "who am I" internally (via `client.auth.session.user.id`) rather than making ViewModels pass a user id around — same reasoning as the `AuthServicing` abstraction, keeps auth-awareness contained to the Service layer.
- `RecipeDetail` (joined recipe + ingredients + tags via Postgrest embedding, `recipes.select("*, ingredients(*), recipe_tags(tags(name))")`) is a separate model from the plain `Recipe` used by the list screen — the list doesn't need the join, so it shouldn't pay for it.
- Liquid Glass: `TabView`/`NavigationStack`/`NavigationSplitView` chrome (tab bar, nav bar, toolbar buttons) gets it automatically from the iOS 26 SDK — confirmed visually (floating pill tab bar, circular glass toolbar button). Custom surfaces opt in explicitly with `.glassEffect(in: <Shape>)` (stat tiles, tag chips, the rating/notes card) and prominent actions use `.buttonStyle(.glassProminent)`. Pattern established in `RecipeDetailView.swift` — replicate for new custom surfaces rather than inventing another card style.
- Theming: `Theme.swift` (`Color.brandPrimary`/`.brandSaffron`/`.brandSage`, the "Warm Kitchen" palette) defines each color's intended role — primary (terracotta) for section headers, stat-tile icons, and hero/thumbnail placeholders; saffron for star ratings; sage for tag chips and "add" affordances — replicate that assignment for new surfaces rather than picking arbitrarily. `AccentColor` mirrors `brandPrimary`, so system-tinted chrome (tab bar, `Color.accentColor` call sites, `.glassProminent`) is on-brand for free. Custom glass surfaces take on a brand tint via `.glassEffect(.regular.tint(Color.brandX.opacity(...)), in: <Shape>)` rather than plain `.glassEffect(in:)`, per `RecipeDetailView`/`AIPlannerView`.
- iPad: only the Recipes tab uses `NavigationSplitView` (list+detail is the one screen with that shape); other tabs stay plain `NavigationStack`, gated on `@Environment(\.horizontalSizeClass)`. See `RecipesTab.swift`.
- Recipe create/update/delete: `RecipeDraft` (title/description/instructions/imagePath/prepTime/servings, no id/userId) is what `RecipeFormViewModel` works with — `RecipeService.create` resolves the current user internally (same pattern as `RecipeRatingService`) and `.update` never touches ownership. Saving a recipe always fully replaces its ingredients and tags (`IngredientService`/`TagService.replaceAll`) rather than diffing — matches the old app's behavior and is much simpler. `RecipeFormView` doubles as both Add (tab root, via `AddRecipeTab`, resets via `.id(_:)` after save since there's nothing to `dismiss()`) and Edit (sheet from `RecipeDetailView`, only shown when `detail.userId` matches the signed-in user — enforced in the UI *and* by RLS). Tags are shared/global (see schema decisions) — `TagService` upserts with `ignoreDuplicates: true` since the `tags` table intentionally has no UPDATE policy.

- Calendar: `MealPlanWithRecipe` (joined via `meal_plans.select("*, recipes(title)")`) and `MealPlanDraft` follow the same Service-layer patterns as Recipes — so the calendar is **account-synced** (per-user, RLS-enforced) the same way Recipes are; there is no realtime layer anywhere in the app, so cross-device sync happens on load, pull-to-refresh, and (added) on the app returning to the foreground (`scenePhase == .active` in `MealCalendarView`). `MealCalendarViewModel.weekDates` is 7 fixed `"yyyy-MM-dd"` strings computed with a UTC calendar — any view code displaying these must format with a UTC `DateFormatter` too, or the shown day can shift by one in non-UTC time zones (`MealCalendarView` builds all its display formatters via a private `utcFormatter(_:)` helper). `todayDate`/`isToday(_:)` on the view model drive the "Today" highlight (`weekDates.first`, since the week starts at the reference date). Each planned meal renders with a meal-type icon + brand tint from `MealTypeStyle` (`Models/`, pure/unit-tested — case-insensitive, neutral fork-knife fallback for unknown types). The view is a Google-Calendar-"Schedule"-style agenda list (one glass-backed card of the week's 7 days, a leading date column — weekday abbrev over day number, filled brand circle + leading accent bar + row tint on today — beside each day's holiday + meal rows, hairline dividers between days), **not** the earlier day-card grid. Layout is size-class-gated like `RecipesTab`: iPhone (compact) stacks the Quick Planner above the agenda in one scroll; iPad (regular, incl. **landscape**) puts the planner in a fixed ~340pt sidebar beside the agenda, whose width is capped (`agendaMaxWidth` 640) and centered so a wide/landscape screen reads as a centered schedule column instead of edge-to-edge rows. iPad already permits all four orientations in `Info.plist` — the redesign is what makes landscape actually *look* right. Holidays: `HolidayProvider` (`Services/`, pure/unit-tested, zero network) maps a "yyyy-MM-dd" day to a `Holiday` (name + SF Symbol) covering US fixed-date, nth-weekday (MLK/Presidents'/Memorial/Labor/Thanksgiving/etc.), and Easter (computus) holidays; `MealCalendarViewModel.holiday(for:)` is a thin passthrough so the view stays dumb, and holidays render as a saffron-tinted chip above that day's meals.
- Recipe catalog scale: `RecipeService.fetchPage(offset:limit:matching:tag:maxPrepTime:)` replaced `fetchAll()` (and the old `Pagination.fetchAllPages` fetch-everything helper, now deleted) once the catalog was sized for Stage 8's 15K+ row import — it selects only list-relevant columns and pushes search server-side via a trigram-indexed (`recipes_title_trgm_idx`) `ilike` filter, rather than loading the whole table and filtering in memory. `RecipeListViewModel` (infinite scroll via `loadMoreIfNeeded(currentItem:)`, called from each row's `.onAppear`) and `MealCalendarViewModel`'s Quick Planner search both debounce `searchText`/`recipeSearchText` through the shared `Debouncer` helper before re-querying from offset 0 — replicate this pattern (fetchPage + Debouncer) for any other view that lists or searches recipes. A 3-arg `fetchPage(offset:limit:matching:)` convenience (protocol extension) forwards to the full method with nil filters, so the Calendar Quick Planner call site stayed untouched.
- Recipe list filtering: the Recipes list has a toolbar filter `Menu` (`RecipeListView.filterMenu`) — a **Category** section (tag names, split into a fixed-order Course group [`RecipeListViewModel.courseTagOrder`] and an alphabetical Cuisine group, both DB-driven from `TagService.fetchAllNames()` so the menu reflects the actual imported catalog) plus a **Max Prep Time** picker (`prepTimeOptions`). Both filters are server-side and paginate: tag → a Postgrest inner-join embed (`recipe_tags!inner(tags!inner(name))` + `.eq("recipe_tags.tags.name", ...)`), prep time → `.lte("prep_time", ...)` (passed as `String`, since `Int64`/filter values must be strings). Filter changes reload from offset 0 through the same `Debouncer` as search. `hasActiveFilters`/`clearFilters()` drive the filled-icon state and reset; the empty state distinguishes "no matches" (search/filter active) from "empty catalog" via `isFilteringOrSearching`. Backed by `recipes_prep_time_idx` (btree on `prep_time`) alongside the existing trigram + `recipe_tags_tag_id_idx`.
- Catalog test-data import: `scripts/import_atk_recipes.py` loads the old web app's `atk_recipes.json` (14,601 ATK recipes at `/Users/bvj13/source/vj-test-kitchen/atk_recipes.json`) into Postgres — it generates SQL and pipes it to `psql` (no Python DB driver needed; psycopg isn't installed). Each recipe is one data-modifying CTE (`WITH r AS (INSERT…recipes…RETURNING id), ing AS (INSERT…ingredients…)` then a `recipe_tags` insert or bare `SELECT id FROM r`) so the identity-generated `recipes.id` threads into its children in a single statement; tags are pre-seeded once with `ON CONFLICT DO NOTHING`. Recipes import **unowned** (`user_id NULL`) by default = shared read-only catalog test data (nobody edits them via the app; keeps the import uncoupled from any auth user); `--owner <uuid>` attributes them to a real account. `--limit` (default 250, 0 = all), `--offset`, `--db-url` (default local stack), `--reset-catalog` (deletes only existing unowned recipes, so re-runs are idempotent and never touch user-created rows), `--dry-run`. Same code path for 250 or the full 14.6K — just change `--limit`. The app targets the **remote** project, so to see imported data in the app either run the script against remote (`--db-url` with the remote Postgres connection string + DB password) or point the app at the local stack.
- Grocery List: **account-synced** via the `grocery_items` table (private per user, RLS `grocery_items_all_own`, same shape as `meal_plans`/`recipe_ratings`) — this **reverses** the earlier "keep it in UserDefaults, no table" decision (see DECISIONS.md, 2026-07-06, both entries) once the user asked for a cross-device checklist with per-item checked state and categories. `GroceryItem` (id/name/amount/unit/`category`/`isChecked`/`sourceRecipeId`/`sourceRecipeTitle`) is a concrete standalone row — deliberately *not* a row in the recipe-scoped `ingredients` table (whose RLS requires an owned `recipe_id`). `GroceryItemService`/`GroceryItemServicing` (fetch/add/addMany/setChecked/setCategory/delete/clearAll) resolves the current user internally like `RecipeRatingService`; the old `GroceryListStore`/`UserDefaultsGroceryListStore` is gone. `GroceryItem` decodes `category` leniently (unknown key → `.other`) so one bad row can't fail the whole list; its custom `init(from:)` is the reason it's not a plain synthesized `Codable`.
  - Category is guessed by `GroceryCategorizer.categorize(_:)` (`Services/`, pure/unit-tested) — a two-pass keyword engine (multi-word phrases like "orange juice" beat single tokens like "orange"; token matching with plural stripping avoids substring traps like "butternut" → butter). Result is stored on the row and user-overridable, so improving the vocabulary needs no migration. `GroceryCategory` (`Models/`) is declared in aisle order so `allCases` doubles as the by-category section order.
  - `GroceryListView` is a checklist `List` with a `Grouping` segmented toggle: **by recipe** (a section per `sourceRecipeTitle`, alphabetical, with manually-added items under "Other Items" last) or **by category** (aisle sections). Tapping a row toggles checked (optimistic, reverts on error — same pattern for setCategory/delete/clear); checked items strike through and sink. Overflow menu (leading `ellipsis.circle`) holds Export-to-Reminders + Clear List; trailing `+` opens `AddGroceryItemSheet` (which live-suggests a category from the typed name until the user overrides the picker). `ReminderService`/`ReminderExporting` (EventKit, `NSRemindersFullAccessUsageDescription`) is unchanged; export sends **unchecked** items only.
  - Recipe → grocery: `RecipeDetailView`'s per-ingredient `+` (→ `addIngredientToGroceryList`) and header "Add All" (→ `addAllIngredientsToGroceryList`) insert concrete `GroceryItem` rows tagged with the recipe's id+title (title is a *snapshot* — a later recipe rename/delete won't move or drop the item; the FK is `ON DELETE SET NULL`). There is no more whole-recipe live-aggregation or `isInGroceryList` toggle — adding is a one-shot copy. `addedIngredientIds`/`didAddAllToGroceryList` are transient per-session checkmark feedback only.
- AI Planner: `supabase/functions/ai-chat` has **zero external imports** (`Deno.serve` + built-in `fetch`/`Deno.env` only, plus a local relative import of its own `search.ts`) — deliberately, after discovering `supabase functions deploy`'s bundling container couldn't resolve DNS on its managed Docker network in this environment (see DECISIONS.md, 2026-07-06). If a future function genuinely needs an npm:/jsr: package, expect to hit this again. Client side follows the same Service/protocol pattern as everywhere else: `AIServicing`/`AIService` wraps `client.functions.invoke("ai-chat", ...)`. The function no longer serializes the whole recipe catalog into the prompt (that stopped scaling once the catalog was sized for 15K+ rows) — `search.ts`'s `runGeminiWithTools` gives Gemini a `search_recipes` tool (title/tag search, capped at 25 results) and loops `generateContent` calls (bounded by `MAX_TOOL_ROUNDS`) until it returns a plain-text answer instead of another tool call. `search.ts` is split out from `index.ts` specifically so `index.test.ts` can import its pure logic (`buildSearchRecipesUrl`, `runGeminiWithTools` against a mocked `fetchImpl`) without triggering `index.ts`'s module-top-level `Deno.serve(...)` as a side effect. **Variety + history:** the chat is stateful — the client (`AIPlannerViewModel.historyPayload`) sends the whole conversation (capped to the most recent ~12 turns) as a `messages` array, not just the latest prompt, so follow-ups ("something else") have context; `normalizeChatTurns` (in `search.ts`, unit-tested) validates/caps it and still accepts the legacy single-`prompt` shape used by `PlanMealIntent`/Siri. To avoid the concierge repeating the same handful of recipes on repeated asks, `search_recipes` fetches a wider **pool** (`SEARCH_RECIPES_POOL_LIMIT`) and `searchRecipes` **shuffles** it before slicing to the requested count (ordering by `id` alone made identical queries deterministic). `AIServicing.sendMessage` takes `[AIChatTurn]`; a protocol-extension `sendMessage(String)` convenience keeps single-turn callers unchanged. **The function is backward compatible (accepts `prompt` or `messages`), but the client now sends `messages`, so `supabase functions deploy ai-chat` must land before/with any client ship or the deployed function will 400.**
- Siri: `PlanMealIntent`/`VJTestKitchenShortcuts` (`VJTestKitchen/AppIntents/`) live in the main app target — no separate Intents extension, no Siri entitlement needed (that's only for the older SiriKit `.intentdefinition` approach). Reuses `AIService` directly since it runs in-process.
- Settings: reached via a "Settings" row in `ProfileView` (pushed via `NavigationLink`, not another sheet). `AppearanceMode` (system/light/dark) is the first setting; `SettingsViewModel` persists it through `AppearanceStoring`/`UserDefaultsAppearanceStore` (same protocol-store pattern as `GroceryListStoring`) and is owned once at the app root (`VJTestKitchenApp`), injected via `.environment`, so both the root scene and any sheet can read it. **`.preferredColorScheme` set on the `WindowGroup` root does NOT propagate into `.sheet` content** — sheets get their own presentation context in SwiftUI — so `AccountButton` re-applies `.preferredColorScheme(settingsViewModel.appearanceMode.colorScheme)` on the `ProfileView` sheet itself; confirmed by screenshot that omitting it left the sheet on the device's own appearance while the root view had already switched. Any future sheet/fullScreenCover will need the same re-application if the override must hold there too.
- Home: the first tab and default landing screen (`HomeTab`/`HomeView`, `HomeViewModel`) — a Liquid Glass dashboard, size-class-gated like `RecipesTab`/`MealCalendarView`. Three sections top-to-bottom: a context-aware suggestion header, a row of three glanceable stat tiles (total recipes / meals this week / grocery items to buy), and a **responsive grid** of suggested recipes (`LazyVGrid` with `GridItem(.adaptive(minimum:))` — ~2 columns on iPhone, ~4 on iPad — deliberately **not** a horizontal carousel, so the grid fills the width without side-scrolling; width-capped/centered for landscape). No this-week list or quick-actions section — the stat tiles themselves are the cross-tab jumps. **Recipe creation is not its own tab** — it's a `+` toolbar button on the Recipes list (`RecipeListView`) that presents `RecipeFormView(mode:.create)` as a sheet and reloads the list on save; the old `AddRecipeTab` is gone. Cross-tab navigation uses a single `AppTab` selection `@Binding` owned by `MainTabView` and threaded into `HomeTab`/`HomeView` (each stat tile sets `selection` to jump); replicate that binding rather than reaching for `NotificationCenter`/deep-link hacks if another screen needs to switch tabs. Suggested cards navigate via `.navigationDestination(for: Int64.self)` (recipe id) → `RecipeDetailView`. Note `HomeViewModel` still loads this week's meals purely to back the "This Week" stat-tile count even though the meal *list* isn't shown.
- Widgets: a WidgetKit extension ships home-screen (iPhone/iPad) **and** desktop (macOS) widgets — three of them: **Cook's Idea** (the `RecipeSuggester` suggestion + a few matching recipes), **Today's Meals** (the current day's planned meals with `MealTypeStyle` icons), and **Grocery List** (still-to-buy count + preview). Same two-target/one-source-glob shape as the app: `VJTestKitchenWidgets` (iOS) + `VJTestKitchenMacWidgets` (macOS) both glob `VJTestKitchenWidgets/` (the `@main WidgetBundle`, timeline providers, and views — kept out of the app targets' glob so there's no duplicate `@main`) plus `Shared/`. **The widget process has no Supabase session**, so it's display-only: the app publishes small denormalized snapshots (`Shared/WidgetSnapshots.swift` — deliberately primitive, no `MealTypeStyle`/`Theme` deps so they compile into the light widget module) into an **App Group** container (`WidgetDataStore`, `group.com.bvj303.vjtestkitchen` on iOS, **Team-ID-prefixed** `89R449GG5Z.group.…` on macOS — a real cross-platform gotcha, resolved per-platform in `WidgetSharedConfig.appGroupIdentifier` and matched by the two widget entitlements files), and the widget just decodes them. The domain→snapshot mapping lives app-side in `WidgetSnapshotBuilder` (pure/unit-tested), driven through a `WidgetPublishing`/`WidgetPublisher` protocol injected into `HomeViewModel`/`MealCalendarViewModel`/`GroceryListViewModel` (default `WidgetPublisher()`, tests can spy) — the grocery VM republishes from `items`' `didSet` so every add/toggle/delete stays in sync. Publishing is best-effort and never throws. Taps deep-link via the app's existing `vjtestkitchen://` scheme (`vjtestkitchen://calendar`/`grocery`/`home`), routed in `VJTestKitchenApp.onOpenURL` through `AppTab(deepLinkHost:)` (which returns nil for the auth `login-callback` so that still falls through to `handleAuthCallback`). Lock-screen accessory families are `#if os(iOS)`-guarded (unavailable on macOS). Widget brand colors are re-declared locally (`WidgetBrand`) to mirror `BrandColor` without pulling in `Color.dynamic`/`Platform` shims. **App Groups need the entitlement registered in the developer portal for device/distribution builds** (automatic signing handles it locally; simulator ignores signing).
- Recipe suggestions: `RecipeSuggester` (`Services/`, pure/unit-tested, zero network/location/AI — same shape as `HolidayProvider`/`MealTypeStyle`) maps two calendar signals to a `RecipeSuggestion` (headline + subtitle + SF Symbol + a title `keyword` + optional `maxPrepTime`): **weeknight vs. weekend** (Mon–Thu cap prep time at 30 min; Fri–Sun relax it for showpiece cooking) and **season** (from the month — soups in winter, grilling in summer, etc.). `HomeViewModel` feeds `keyword`/`maxPrepTime` straight into `RecipeService.fetchPage` and falls back to an unfiltered page when a seasonal keyword matches nothing (guards partial/local catalogs) — keywords are deliberately common ATK title words so the trigram `ilike` reliably returns matches. Weather was intentionally left out to keep this purely calendar-derived (no new entitlements/permissions), even though Open-Meteo infra exists for the Calendar. `RecipeService.totalCount()` (a HEAD-count query) backs the catalog-size stat, declared as a protocol requirement with a default (returns 0) so existing test fakes needn't implement it.

## Reviewing changes in the simulator
The user reviews completed features **in the running app on both form factors**, not just from tests or screenshots. As the final step of a feature/bugfix (after tests pass), run `scripts/review-sims.sh` — it builds once and installs+launches the app on a booted iPhone **and** iPad simulator (layouts are size-class-gated, so both matter). Device names are overridable via `REVIEW_IPHONE`/`REVIEW_IPAD` env vars. From a **background-job** session this cannot tap/navigate the simulator (see Status' note on the assistive-access limitation) — the app just launches and the user drives it; to force a specific screen in a screenshot, temporarily default to it / inject sample data behind a clearly-marked `TEMP` block and revert before commit.
